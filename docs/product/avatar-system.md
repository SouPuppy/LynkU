# 头像系统：现状分析与交互设计

日期：2026-09-23。状态：已实施，并在用户授权后随全量更新同步云端，待手机真机审核。依据用户提供的 `assets/avatar/anonymous.png` 与四张 `avatar_01`–`avatar_04` 素材；保留现有页面，无上传入口。原图未改，未 commit、未提交微信正式发布、未批量修改用户资料。下述现状表记录实施前问题，当前实现与证据见末节。

## 1. 设计结论

普通头像是账号资料；匿名头像是当前内容或会话的身份展示。二者分开管理。

- 四张猫头像供用户选择；第一张为统一默认，不在登录、刷新或失败时随机变化。
- 匿名小幽灵只用于匿名状态，不出现在账号头像选择器中。
- 更换普通头像不退出匿名模式，也不改变已有帖子、评论或私信的匿名属性。
- 每个界面按其实际对象的身份展示头像，不能根据浏览者的全局匿名开关替别人换头像。
- 已有账号、邮箱认证和微信关联保持原状；空头像通过显示回退处理，不读时批量改库。

这四张默认图并非四种身份、等级或性别，也不是唯一身份标识。不同用户可以使用相同头像，仍由昵称和已有会话名称帮助辨认。

## 2. 现状与问题

| 代码或资源证据 | 当前表现与影响 | 设计处理 |
|---|---|---|
| `components/avatar/avatar.ts` 引用旧 default-avatar/anonymous | 新素材未接入；匿名路径还分散在多处 | 单一资源定义，所有展示入口一致 |
| 设置页只有“修改昵称” | 用户无法选择四张默认头像 | 原列表增加一行“头像”，复用现有弹层 |
| 五张原图均为 1254 × 1254，总计 4,968,797 字节 | 超出小头像实际显示需要，增加资源成本 | 保留原图，生成轻量运行素材，明确排除原图打包 |
| `update-profile.ts` 仅验证 avatar_url 字符串与长度 | 可绕过界面写入任意 URL、临时地址和匿名资源 | 服务端只接收四张预设中的头像 |
| 头像错误处理仍设置相同后备地址 | 缺失的后备资源没有明确终止状态 | 有界回退，最终使用中性占位；匿名绝不回退到账号图 |
| 现有 profile_version、资料事务与 outbox | 可传播实名资料，已排除匿名帖子/评论/通知 | 复用这条链路，不另做头像同步系统 |

原素材已经具有一致画风：淡蓝／淡紫底、圆形构图，四张猫与一张小幽灵区分明确。保留图形与色彩；视觉变化集中于正确使用和清晰选择。

## 3. 展示规则

| 场景 | 显示内容 | 是否允许改头像 |
|---|---|---|
| 新账号、旧账号头像为空 | 第一张猫头像 | 在设置选择四张之一；游客取得微信身份后同样可用 |
| “我的”处于普通模式 | 已保存的账号头像 | 从设置进入 |
| “我的”处于匿名模式 | 小幽灵，保留现有匿名状态提示 | 仍从设置修改普通头像，不影响当前匿名展示 |
| 设置页“头像”行 | 账号头像，并标注“用于非匿名展示” | 可以；该页是本人私有资料管理页 |
| 非匿名帖子、评论、互动通知 | 作者当前合法头像 | 资料变更通过已有链路同步 |
| 匿名帖子、评论、互动通知 | 固定小幽灵 | 不可更换；无账号头像或来源链接 |
| 私信目录／聊天中已有头像的位置 | 按对端在该会话中的可见性显示 | 匿名对端始终小幽灵，昵称身份对端使用普通头像 |
| 身份尚未确认 | 中性占位 | 不先闪出账号头像再替换成匿名图 |
| 已删除或不可用的用户 | 中性占位及原有不可用说明 | 不借用小幽灵表达“已删除” |

不为当前没有头像的列表或气泡新增一排头像。保留现有页面信息密度。全局匿名开关不修改历史内容，也不把已建立的昵称身份会话变成匿名会话。

## 4. 最小界面设计

在设置页现有“修改昵称”上方新增一行，复用原有行高、间距、分隔线和右箭头：

```text
学校邮箱                         已认证 >
头像                     [当前圆形头像] >
  用于非匿名展示
修改昵称                          昵称 >
```

点“头像”后使用当前修改昵称弹层的尺寸、圆角、白底、遮罩和按钮样式。内容为“选择头像”、四张头像的 2 × 2 网格，以及“取消 / 保存”。不另建资料页、不改导航、不加入头像商城、上传、裁剪或动画。

- 默认选中已保存的预设；当前为旧头像时，设置行安全回退为默认图，四项均不预选，用户主动选择后才可保存。不加载未经审核的旧远程图片。
- 每个选项使用现有 lg（120rpx）圆形头像，点击区域适当放大；选中项加原主色描边及小勾选，不能只依靠颜色。
- 图片自身保留原画颜色；不将猫头像染成深色，不叠加身份徽章。匿名提示沿用既有文字和局部结构色块。
- 屏幕阅读标签为“头像 1”至“头像 4”和“已选中”；无需给普通用户添加四套人格说明。
- 弹层说明固定为“用于非匿名展示，匿名时仍显示统一头像。”
- 当前个人页头像不增加隐蔽点击行为，以免匿名小幽灵被理解为可单独设置的匿名身份。

## 5. 保存与错误状态

| 状态 | 用户看到什么 | 行为 |
|---|---|---|
| 尚未改变选择 | 当前选择清晰标记，保存不可用 | 不重复提交 |
| 选择新头像 | 只更新弹层预览 | 外部头像仍是已保存值 |
| 保存中 | 原保存按钮显示“保存中”，禁止重复提交与切换 | 不同时提交昵称修改；关闭弹层不等同取消已发请求 |
| 保存成功 | 弹层关闭，“头像已更新” | 更新本人资料缓存和可见入口 |
| 保存失败／结果未确认 | 留在弹层，保留选择，“暂未确认保存，请重试” | 重试同一头像，服务端相同值不重复产生资料版本 |
| 主动取消，尚未保存 | 关闭弹层 | 不修改账号、不改变匿名开关 |
| 切账号或离开页面后收到旧结果 | 无旧页面提示与覆盖 | 按现有账号／页面代际丢弃过期界面回写 |

资料更新以服务器确认的头像为准；非匿名历史内容的异步投影允许短暂延迟。不能通过修改本地所有匿名对象来追求“即时同步”。本人资料立即更新，其他页面按既有刷新取得新版投影，不新增每个头像自己的轮询。

## 6. 隐私及资源边界

匿名展示必须先在服务端剥离真实资料，再在客户端按匿名状态强制选择小幽灵。匿名响应不能包含真实头像地址、文件名、账号头像序号或可跨会话关联的自定义头像标记。不能仅用 CSS 隐藏真实图片；匿名状态下也不得提前请求真实头像资源。

图片回退分两条：

- 普通展示：合法已保存图 → 第一张默认图 → 中性占位。
- 匿名展示：小幽灵 → 中性占位，仍保留匿名文字；绝不尝试账号图。

更换来源或身份后，旧图片的迟到错误事件不能覆盖新状态。后备图片自身失败后终止重试，不循环触发相同请求。

新写入只允许四张预设。旧外部头像不能因为格式是 HTTPS 就自动视为可信：实施时核对现有可信资源配置；只有已审核来源可继续显示，未知来源安全回退，保留原始记录供后续审查。不能在未盘点的情况下声称历史头像迁移完成，也不因本轮设计删除真实数据。

## 7. 实现结构与资源规格

保留现有 avatar_url 字段和 users.updateProfile 接口；存规范化的预设路径，无需新增头像表、上传服务、身份映射或第二套资料缓存。一个共享头像定义维护四个选项、默认项、匿名项和合法来源规则；前后端都使用同一份定义。

保留用户原始 PNG，不覆盖、不重新绘制。建议运行版统一为 256 × 256 PNG，先检查保留渐变的压缩效果；五张合计目标不超过 250 KB，此数是待验证目标，不是已达到的结果。继续使用现有 56/80/120rpx 三档显示。检查小尺寸辨识度和深色背景白边，不自行更改构图。

构建链同时生成运行图、检查资源存在及体积，并显式排除原图打包。运行路径独立于原图路径，旧匿名路径不再保留映射或文件。不得假设开启“忽略无引用资源”就一定正确处理动态头像路径；实际预览包应检查运行资源是否齐全、原图是否被排除。

## 8. 验收条件

1. 四张普通头像都可保存，重进页面及重新取得微信身份后保持一致；不在每次加载时随机改变。
2. 在匿名模式中更换普通头像后仍显示小幽灵，退出匿名恢复刚选的头像。
3. 匿名帖子、评论、通知及双向匿名私信不返回、请求或闪现账号图；普通内容不被浏览者的匿名开关覆盖。
4. 服务端拒绝任意 URL、临时路径、未知预设及把小幽灵保存为普通资料头像。
5. 断网、重复点击、迟到响应、切账号、图片失败均保持稳定；匿名回退不泄露真实图片。
6. 资料传播覆盖非匿名内容并排除匿名内容，保留所有账号认证状态；旧来源未经审查不直接加载。
7. 现有三档圆形尺寸及弹层在小屏、深色结构附近清晰；运行包不夹带五张原图。

## 9. 当前实现与审核

旧 `assets/default-avatar.png` 和 `assets/anonymous.png` 已在确认生产源码无引用后删除。现有 avatar 组件已替换为新实现并继续作为唯一展示入口，不存在并行旧头像系统。测试中的旧路径仅用来验证拒绝非法写入和匿名覆盖，不是兼容入口。账号历史字段不在这次源码清理中批量删除；未知值安全回退属于新系统的输入保护。

共享头像定义位于 `packages/contracts/src/avatar.ts`。所有匿名资源投影使用同一常量，聊天展示契约也强制覆盖匿名对端的图片。设置页提供四选一弹层，成功确认后更新会话资料，保存失败保留选择；昵称与头像共用保存锁。新账号存第一张预设；旧账号原始头像字段不被读时修改。本轮没有已审核的旧远程头像白名单，因此旧地址仅保留于存储，界面回退为第一张，不发外部图片请求。

构建工具 `tooling/build-avatar-assets.cjs` 保留五张原图，生成 256 × 256 运行 PNG，合计 241,212 字节（约 236 KiB），相对原图减少约 95%。已查看小幽灵运行图，保持原构图与渐变。运行图随 `build:contracts`／`typecheck:client` 生成；`npm run configure` 生成明确的原图排除、运行图包含规则。增加构建期 PNG 工具的显式开发依赖，不新增客户端或云端运行依赖。

本地行为覆盖：四种预设更新、相同值重试与事务回滚、非法及匿名资源写入拒绝、游客选择、匿名开关保持、失败重试、过期账号响应隔离、旧图片失败隔离与回退终止。资源检查验证原图哈希不变、输出尺寸／体积及打包配置。完整检查见 `dist/avatar-implementation-check.log`，实际通过情况以[状态表](../plans/refactor/status.md)为准。

人工审核入口：设置 → 头像；选择四张中的任意一张保存，再在“我的”切换匿名。验证匿名始终显示小幽灵，恢复普通模式后保留所选图片。再检查帖子、评论、私信列表和互动通知的现有头像位置。

已在用户授权后部署全部 8 个云函数并校验云端代码与配置，客户端真实 preview 成功，总包 847,936 字节。微信开发者工具中五张头像资源均读取成功为 256×256（`dist/chat-page-live-smoke.json`），证明新路径实际可用；旧头像值无需批量改库。真实资料保存／投影传播及手机真机弹层／圆形视觉仍待验证，不把资源读取通过当作全部头像交互通过。最新证据见唯一状态表。
