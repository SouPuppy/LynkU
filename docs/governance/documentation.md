# 文档与决策治理

状态：本轮生效的维护规则。

## 各类文档只解决一个问题

| 位置 | 职责 | 更新时机 |
|---|---|---|
| 根 README | 产品介绍、当前启动入口 | 用户进入项目的方式变化 |
| 根 AGENTS.md | Codex 必须知道的约束与导航 | 稳定工作规则变化 |
| docs/README.md | 权威文档地图及状态 | 新增/替换规范 |
| docs/product | 产品行为、权限与非目标 | 产品行为有意改变 |
| docs/architecture | 边界、契约和已选择的结构 | 依赖/数据/接口边界变化 |
| docs/architecture/decisions | 简短 ADR：理由与代价 | 有意义的架构选择被确定/替换 |
| docs/governance | 代码、文档、验证标准 | 检查方式或工作约定变化 |
| docs/plans/refactor/status.md | 本轮状态、证据、下一步、阻塞 | 一个工作切片完成或出现真实阻塞 |
| docs/runbooks | 可执行的环境、迁移、发布与恢复流程 | 命令、配置、运行方式改变 |
| 测试/schema/manifest | 可执行的行为及结构真相 | 同批代码修改 |

每条规则指定一个权威位置，其他文档链接到它。说明性导航可摘要，但不要维护三份权限矩阵、两份迁移状态或多套命令名称。

## 目标与现实必须分开

文档开头标明“目标规范”“已实现”“历史记录”或“运行手册草案”。计划里的未来目录/命令必须注明未实现；实际命令由 package scripts 验证后再写入当前开发指南。

发现实现与目标不一致时，区分：产品规则变化、已知缺陷、迁移暂存、陈旧文档。缺陷不能通过修改目标来洗掉；有意变更必须说明原因和验收影响。

`status.md` 不重复全量测试日志，记录命令、结果、执行环境/版本以及可定位证据。没有真正运行的检查写“未执行”，不能用“预计通过”充当证据。

## ADR 模板

一个决策通常一页以内，字段如下：

- 编号、日期、状态（采纳/取代/否决）与被替代决策。
- 问题：哪个真实约束需要选择。
- 决定：选择什么，适用到哪里。
- 理由和代价：最多几个实质点。
- 验证：兼容性试验、关键测试或构建证据。
- 迁移/撤回：涉及哪些旧实现，什么条件下重新评估。

目录边界、数据一致性、协议版本、构建方案、重要运行时升级值得 ADR；变量命名和普通函数提取不需要。不要为每次改动再生成一套 PRFAQ、research、audit、spec。

## 历史文档整理

旧 design/research/tickets 是可追溯资料，不默认为现行规范。先建立明确导航与替代关系；R7 按仍被引用、可归档、已废弃分类，必要时移至 docs/archive 并修复链接。

不能仅按文件日期批量删除或认定内容错误。旧 ticket 状态不改成“本轮已完成”；现有 ticket index 测试在归档时应替换为有效的历史链接/完整性校验，而不是让它锁死现行目录。

过去文档中的 Kotlin 后端、独立 JWT、直连私有数据库等方案不能被后续任务无意恢复。只保留历史说明，不作为未完成需求。

## 代码与文档协同

- 改 action/schema：同步契约、兼容说明和关联验收。
- 改集合/索引/权限：同步 manifest、迁移脚本与核对步骤。
- 改目录/脚本：同步 README、DEVELOPMENT、AGENTS 与 CI。
- 改部署：同步环境前提、回滚、错误处理与已测试范围。
- 文档例子使用虚构标识，无真实邮箱、凭据、私信正文或匿名映射。

R7 建立轻量文档检查：本地链接、导航入口、关键命令是否存在、生成文档是否陈旧。避免对普通文档文字做大量脆弱正则测试。

## 长任务的上下文管理

每个切片完成后在 status 中保留：当前阶段、完成证据、下一个明确动作、失败/待验证项、当前兼容层及退出条件。恢复任务先读此文件并核对代码，不能从聊天末尾猜测全局进度。

临时探索结果只有形成决定或阻塞时才进入长期文档。不要把终端输出、思考过程和重复周报变成新的规范。根 AGENTS 保持短小，按职责引导到相关文件；只有存在真实目录特有约束时增加局部 AGENTS。
