# 聊天 UI 体验调查：在现有范式内精修

日期：2026-09-24。状态：调查与建议，未实施。用户要求调查当前聊天界面为何显得原始，保持现有 UI/UX，不增加花哨视觉、不重设计。本轮不修改业务源码、不部署、不发送真实消息。

## 结论与边界

现有蓝白气泡、灰色阅读背景、圆角输入区和页面骨架可以继续使用。粗糙感主要来自三件事：同一消息的不同状态像不同组件；说明与动作没有清晰区分；状态改变时，显示、位置和可执行操作不完全一致。

普通身份说明保持静态是合理的；恢复动作应有明确入口与反馈。无需把每段文字都变成可点击控件。

沿用此前明确边界：不改导航、不新增聊天头像或来源卡片、不搬迁屏蔽入口、不新增更多菜单、不重新分组时间、不反转整个输入区。匿名身份提示保留局部深色。图片、语音、在线状态和“正在输入”不属于本轮范围。

## 现状证据与影响

| 优先级 | 当前实现 | 用户会感受到什么 | 最小优化建议 |
|---|---|---|---|
| P1 | 待确认消息由页面的 pending 模板渲染；确认后转到 chat-bubble，内边距、换行、行高与外部间距不同 | 同一段正文在发送成功时变形；像两个功能拼起来 | 统一一个气泡呈现，确认时主要更新状态和回执 |
| P1 | 所有 pending 永远排在所有 confirmed 消息之后 | A 未确认、B 先确认时，B 出现在 A 上方；确认时可能再次换位置 | 同一个显示列表统一关联操作编号与确认结果，避免两套列表引起额外跳动；最终排序仍以服务端序号为准 |
| P1 | 同一失败项点击后，输入框为空则移回编辑，有内容则查询并重发 | 用户无法从界面预期点击结果 | “重试”和“修改”各自固定含义；已有输入时明确处理冲突，不覆盖、不偷偷改动作 |
| P1 | 文案“点击检查”对应的 retry 会在查询为空后发送 | 提示承诺与操作不一致 | 使用准确的“重试”；沿用现有先查询、必要时原编号发送机制，查询中有就地反馈 |
| P1 | 发送按钮只判断原始字符串是否为空；发送逻辑会 trim | 只输入空格时按钮亮，但点击没有结果 | 按同一份有效正文判断是否可发送 |
| P1 | 空态只检查 messages.length；pending 单独渲染在其后 | 第一条正在发送时仍显示“暂无消息” | 历史与待确认都为空才出现空态；保持简洁，不添加插画 |
| P1 | “正在发送”也绑定恢复点击；屏蔽和解除没有操作中状态 | 哪些可点、是否已受理不清楚 | 非操作状态不响应；操作中显示“处理中”，阻止重复触发 |
| P2 | 查看更早、未读分界和新消息入口共用 history-control 样式 | 动作与纯说明长得相同 | 静态分界保持弱化；操作使用明确动词、轻按压态与足够点击范围，位置不动 |
| P2 | 一次同步或已读回执错误都会显示整行黄色警告 | 偶发回执错误让整个聊天看起来不稳定，消息区可用高度随之变化 | 区分同步与回执失败；短暂故障先原位轻提示，持续失败才强调 |
| P2 | 每条消息均显示相对时间和正常发送回执，时间只在消息属性观察器运行时格式化 | 连续消息出现很多“刚刚／已发送”，时间长期停留也不准确 | 时间仍放原位置，使用稳定的时刻；普通回执降低权重，异常更明显，不新增时间分组 |
| P2 | 未发送正文只保存在页面 data，持久化队列仅覆盖已提交消息 | 后台回来同页还在，返回列表再进则丢失 | 先补已有会话的本地输入保留，按当前账号与独立会话隔离 |

## 信息和视觉如何组织

保留现有区域，以字号、间距、文字颜色和轻量按压态明确各自职责，不新增一套组件外观。

| 原有区域 | 平时承担的职责 | 需要强调的时机 |
|---|---|---|
| 顶部身份提示 | 清楚回答“我以什么身份说话，对方看到什么” | 身份未确认、身份加载失败；匿名局部深色稳定表示身份，不随网络状态变色 |
| 屏蔽所在行 | 保留可找到的保护入口，正常时次于对话正文 | 正在处理或已屏蔽时提供明确反馈，不增加常驻大警告 |
| 消息正文 | 页面最主要的阅读内容；同一条正文在不同状态保持一致排版 | 不因后台确认结果改变字号、换行或气泡尺寸规则 |
| 每条消息下方 | 次级时间与回执 | 异常原因、可执行恢复动作提高可见性；普通成功状态保持安静 |
| 历史与新消息提示 | 表明阅读位置、提供跳转动作 | 有新消息但用户正在读历史时提示，点击后才跳转 |
| 输入区 | 明确当前能否发送，保护正在写的内容 | 接近长度限制、发送受限时在相关位置说明，不额外铺满提示 |

“单纯展示”需要逐项判断：身份、时间、已读本来就是说明；查看历史、恢复失败和屏蔽则需要成为完整的操作。成熟感来自信息职责清楚、动作结果可预期、状态变化连续，而不是增加可点击元素的数量。

## 建议的第一批精修

### 1. 一条消息从输入到确认保持连续

沿用现有左右气泡、宽度和颜色，统一正文渲染。发送中、待确认、明确失败及确认成功都保留同一条消息的关联标识，恢复失败原文不会生成另一条视觉副本。

不能简单按客户端时间重排服务端历史。两个请求确实以不同顺序被服务端接受时，最终应遵循真实序号；本次要消除的是“pending 全部放最下面”与换模板带来的额外变动。历史阅读锚点与底部跟随需要一起验证，不引入通用消息框架。

### 2. 状态说明和恢复动作各司其职

| 状态 | 原状态行中的说明 | 可执行动作 |
|---|---|---|
| 正在发送 | 正在发送… | 无；避免假可点击 |
| 确认结果中 | 正在确认… | 无；避免重复操作 |
| 结果未确认 | 尚未确认发送 | 重试：先查询，必要时沿用原编号提交；自动恢复仍只查询 |
| 内容被拒绝等需改正文 | 简短原因 | 修改；输入框已有内容时提示处理冲突，不覆盖原输入 |
| 当前权限／屏蔽不允许发送 | 对应原因 | 先解决条件，避免无意义重试 |
| 发送成功／已读 | 原位置的轻量回执 | 无需把普通回执做成按钮 |

不凭错误文案猜测动作，应由已有错误类型决定。正文允许复制的能力继续保留。

### 3. 让输入区真实反映可用状态

空白正文不能发送；首条消息进入待确认状态后立刻退出空态。输入框达到上限附近才显示计数／限制提示，不常驻增加一排信息。

输入焦点、键盘、发送按钮对齐需要实际设备观察后再调。保持现有输入框与发送按钮位置，不预设需要添加工具栏。

### 4. 在原位置区分操作与说明

身份提示在正常状态下只负责说明。异常可恢复时，用清楚的“重试”入口与按压反馈。屏蔽仍在原位置，但首次身份未确认时不可操作，提交中显示进度；解除也应有一致反馈。

查看更早、新消息入口采用现有页面已经使用的轻按压反馈；“以下为新消息”保持纯分界。无需引入新图标体系或新卡片。

## 第二批：阅读节奏与输入保护

顶部已有身份、屏蔽两行，异常时再加一行。可以收口这些区域的边界、间距和信息权重，但不改变位置或把入口藏入新菜单。匿名深色提示继续明确表示本人身份；它不承担网络警告或失败状态。

时间先在原元信息行改用明确时刻，例如“14:32”“昨天 14:32”；暂不执行此前撤回的时间分组。正常回执、时间作为次级信息，失败原因与恢复入口优先被看到。

未发草稿先按“本人＋已建立会话”保存。新发起匿名会话的 initiation_id 每次独立，不能只按来源帖子或对端账号恢复，否则会把不同匿名发起串在一起；未建立会话的恢复入口与清理策略应单独明确后再加入，不借本轮偷偷合并会话。

## 保留已有能力

- 服务端确定本人和对端身份，前端不得猜测身份来降低加载门槛。
- 匿名对端不出现个人头像、资料跳转或跨会话关联线索。
- 只有进入视口的消息确认已读；阅读历史时新消息不强拉到底部。
- 首条未读定位、原编号恢复、隐藏页面停止轮询与迟到响应隔离继续保留。
- 用户正在写的内容、已提交待确认内容分别管理，不能用其中一类覆盖另一类。

## 验证方式与本轮边界

本轮依据当前源码及本地合成运行检查。真实开发者工具自动化连接失败，启动自动化也在 AppID 权限确认后超时，未取得本轮新的截图或视觉测量；上轮的真实加载通过不能替代本轮交互视觉验收。

本地诊断脚本 `dist/chat-ui-review-0924/interaction-repro.mjs` 通过实际 Page、services 与 SendOperations，使用内存 SDK 复现了五个场景；真实云调用为零。证据为 `dist/chat-ui-review-0924/interaction-evidence.json`：

- 首条 pending 为 1、正式消息为 0 时，实际 WXML 条件仍显示空态。
- 模拟服务端依次接受 A、B，但延迟返回 A 的结果：模板集合顺序先为 B、A，确认后恢复 A、B。此处确认的是数据与模板顺序，实际跳动幅度尚未测量。
- 同一明确失败项在输入为空时移回编辑，输入非空时查询并重发，证实动作随另一处输入状态变化。
- 纯空格输入在实际模板中仍允许点发送，但发送调用为零。

以上是问题复现证据，不是修复后的验收结果。重跑入口：`node --import tsx dist/chat-ui-review-0924/interaction-repro.mjs`。本轮只增加调查文档及本地诊断产物，未修改业务代码，未新增兼容层。

需要开发者工具／真机验证：键盘出现与收起后是否留有多余安全区、多行输入时按钮与正文对齐、长昵称与系统胶囊避让、确认后底部是否被遮挡、历史翻页是否保住像素位置、辅助提示变化是否造成跳动。

建议验收用完整短流程：输入两行 → 连续发送 → 模拟一次丢回包 → 继续输入 → 重试或修改前条 → 上翻历史收到新消息 → 返回列表再进。整个过程应看得懂当前状态、知道可执行动作、保住正文，并维持原有页面外观。
