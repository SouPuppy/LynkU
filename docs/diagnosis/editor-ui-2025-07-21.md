# Diagnosis Report: Editor Page UI Audit

- **Date**: 2025-07-21
- **Scope**: `miniprogram/pages/editor/` + dependencies
- **Trigger**: `/diagnose` — 发帖页面 UI 深度分析
- **Renderer**: Skyline + glass-easel

---

## Topology Summary

```
index page (FAB) ──navigateTo──→ editor page
                                  ├── nav-bar (custom, fixed)
                                  ├── categories service (DB read)
                                  └── posts service → cf-posts (cloud function)
```

The editor page (`pages/editor/`) is a simple create-post form: title input,
category pills, content textarea, submit button. It uses the shared `nav-bar`
component for navigation. Navigation entry is via the FAB on the index page.

---

## Findings

Ranked by severity (CRITICAL → WARNING → NOTE).

### CRITICAL-001: Double Top Spacing — Massive Dead Zone Above Form

- **Dimension**: Inconsistency
- **Severity**: CRITICAL
- **Status**: CONFIRMED
- **Classification**: LOCAL_FIX

**Location**:
- `miniprogram/pages/editor/editor.wxss:7` — `padding: 180rpx var(--spacing-md) 0;`
- `miniprogram/components/nav-bar/nav-bar.wxml:11` — spacer `<view style="height: {{statusBarHeight + navBarHeight}}rpx;"></view>`

**What**:

The nav-bar component already renders a spacer view (~176-196rpx) to push
content below the fixed navigation bar. The editor page additionally applies
`padding-top: 180rpx`. These two mechanisms **stack additively**, producing
~356-376rpx of top offset — roughly **double** what is needed.

Every other page in the app relies **only** on the nav-bar spacer and has zero
top padding:

| Page | Top padding | Spacing source |
|------|-------------|----------------|
| index | none | nav-bar spacer only |
| post | none | nav-bar spacer only |
| messages | none | nav-bar spacer only |
| profile | none | nav-bar spacer only |
| search | none | nav-bar spacer only |
| categories | `var(--spacing-md)` (24rpx) | nav-bar spacer + uniform padding |
| **editor** | **180rpx** | **nav-bar spacer + 180rpx = double** |

**Root Cause**:

The comment at `editor.wxss:5-6` reveals the intent:

```css
/* ponytail: 180rpx covers statusBar(≤120rpx) + navBar(88rpx) on all iPhones.
   Nav-bar spacer in glass-easel may arrive late; CSS padding is synchronous. */
```

The developer added CSS padding as a synchronous fallback for a perceived race
condition where the nav-bar component's spacer height is initially 0 (before
`attached()` lifecycle fires and `setData` updates `statusBarHeight`). The
spacer was never removed after this workaround, so both mechanisms are active
simultaneously.

**Calibration**:

`wx.getWindowInfo()` is synchronous in WeChat SDK 3.x+. The "arrives late"
concern is a non-issue on current SDK versions. All other pages in this same
app work correctly with the nav-bar spacer alone — confirming the workaround is
unnecessary.

**Visual impact**: ~180rpx (~90px) of dead whitespace between the nav bar and
the title input. On an iPhone 14 screen (390x844px), this wastes ~11% of the
vertical viewport.

**Fix**: Remove `padding-top: 180rpx` from `.edit-page`. Keep horizontal
padding. One line change, one file.

### WARNING-001: Unused Component Registration

- **Dimension**: Over-abstraction (dead code)
- **Severity**: WARNING
- **Status**: CONFIRMED
- **Classification**: LOCAL_FIX

**Location**: `miniprogram/pages/editor/editor.json:1`

**What**:

`topic-chip` is registered in `usingComponents` but is never used in
`editor.wxml` (nor in any other WXML file in the entire project). Topic pills
are rendered inline with a `wx:for` loop directly in the editor template.

This forces the framework to parse and initialize the component definition on
page load for zero benefit. Dead registration cost is tiny but non-zero.

**Fix**: Remove `"topic-chip": "/components/topic-chip/topic-chip"` from
`editor.json`. One line, one file.

### WARNING-002: No Bottom Safe-Area Padding

- **Dimension**: Under-abstraction (missing edge case)
- **Severity**: WARNING
- **Status**: CONFIRMED
- **Classification**: LOCAL_FIX

**Location**: `miniprogram/pages/editor/editor.wxss:1-9`, `editor.wxss:59-66`

**What**:

The `.edit-page` has no bottom safe-area padding. The submit button sits at
the bottom of the flex column with `margin: var(--spacing-lg) 0`. On devices
with a home indicator (iPhone X+, some Android gesture-nav devices), the button
is partially obscured by the system gesture bar.

Compare with `post.wxss:17` which correctly uses:
```css
padding-bottom: env(safe-area-inset-bottom);
```

The post detail page handles this; the editor page does not.

**Fix**: Add `padding-bottom` with `env(safe-area-inset-bottom)` to
`.edit-page`. One line, one file.

### NOTE-001: Hardcoded navBarHeight Default

- **Dimension**: Inconsistency
- **Severity**: NOTE
- **Status**: DISPUTED (accepted trade-off)
- **Classification**: MONITOR_ONLY

**Location**: `miniprogram/components/nav-bar/nav-bar.ts:12`

**What**:

The nav-bar component hardcodes `navBarHeight: 88` rpx (44px). While
`statusBarHeight` is read dynamically via `wx.getWindowInfo()`, the nav bar
height is not. WeChat's navigation bar is 44px on iOS but can be 48px on some
Android devices.

**Calibration**: The practical impact is ≤4px difference on affected devices.
This is within visual tolerance for a navigation bar. All pages share this
component so the inconsistency, if any, is uniform across the app.

**Disposition**: Monitor only. Fix if Android users report misalignment.

### NOTE-002: No Form-State Preservation on Back Navigation

- **Dimension**: Under-abstraction
- **Severity**: NOTE
- **Status**: CONFIRMED
- **Classification**: LOCAL_FIX (simple draft to Storage)

**Location**: `miniprogram/pages/editor/editor.ts`

**What**:

If the user types content and accidentally taps the back button (or the system
back gesture), all entered text is lost. There is no unsaved-changes warning
and no draft auto-save.

Other WeChat mini programs (e.g., WeChat's own "Moments" editor) persist draft
content to `wx.setStorageSync` on input and restore it on page load.

**Fix**: Add `wx.setStorageSync('draft_post', {title, content, categoryId})` on
each input, restore in `onLoad`, clear on successful submit. Touch 1 file,
backward-compatible.

---

### NOTE-003: Textarea auto-height + flex:1 Interaction

- **Dimension**: Inconsistency
- **Severity**: NOTE
- **Status**: MONITOR_ONLY
- **Classification**: MONITOR_ONLY

**Location**: `miniprogram/pages/editor/editor.wxml:43-50`, `editor.wxss:50-56`

**What**:

The textarea has both `auto-height` (grows with content) and `flex: 1` (grow
in flex container). In glass-easel's flex implementation, `auto-height` takes
precedence — the textarea starts at `min-height: 300rpx` and grows as content
is typed. The `flex: 1` is effectively dead CSS here.

**Disposition**: Current behavior (300rpx minimum, grows with content) is
actually desirable. The `flex: 1` is harmless dead CSS. Monitor only.

## Impact Assessment

The **CRITICAL-001** double-spacing is the "巨大UI问题" — it wastes ~11% of the
viewport with dead space, making the editor look broken compared to every other
page in the app. Fixing it is a one-line CSS change.

The remaining WARNING items are cleanup (dead component registration, missing
safe-area) that improve polish but don't break the visual layout.
