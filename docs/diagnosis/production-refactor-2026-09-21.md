# 上线前重构评估

日期：2026-09-21。基于当前工作区，包括已有未提交改动。

本文保留为源码初评。后续执行阶段与目标规范以 [R0–R8 总计划](../plans/refactor/plan.md)及[文档入口](../README.md)为准，下文原阶段划分不再单独维护。

## 结论与范围

现有项目具备功能原型和初步分层：页面、客户端服务、云函数、私有集合。已有匿名脱敏、服务端认证门槛、部分事务、消息幂等及会话竞态测试，值得保留。

核心问题是业务边界、数据完整性和验证能力还不足以支撑持续迭代。建议保留原生小程序和 CloudBase 的现有运行边界，按业务模块逐步重建内部实现；当前证据不足以支持更换技术栈或拆分微服务。

本次是源码初步评估，不是完整安全审计或线上验收。未连接线上数据库，未验证数据库权限、索引、真实并发行为、设备渲染或发布回滚。业务代码未修改。

## 基线

- `npm run check` 通过：客户端 TypeScript 检查、云函数入口 JavaScript 语法检查、30 项测试。
- `tests/boundaries.test.js` 的 11 项测试主要检查源码模式、文件及文档一致性，不能替代运行时权限和数据行为验证。

## 发现与优先级

### P0：先建立正确性保障

1. **消息同步游标缺少稳定的第二排序键。**
   `cloudfunctions/messages/index.js` 的 `syncConversation` 按 `updated_at` 排序并使用 `gte(since)`，游标只有时间；`miniprogram/services/watch.ts` 在时间游标不前进时停止翻页。如果同一时间的消息超过一页，存在反复读到同一页、无法覆盖其余消息的风险。需要构造同时间超页数据复现，改为稳定复合游标或其他可证明完整的同步协议。
2. **会话列表与未读数由截断的消息样本推导。**
   `listConversations` 分别最多读取 200 条已发送和已接收消息，再聚合会话。旧会话可能消失，未读统计也不能代表完整历史。应建立独立会话摘要与未读模型，并对旧数据提供可重复执行的回填。
3. **写入重试的契约不统一。**
   私信已有稳定消息 ID 与事务；发帖创建直接添加记录，没有请求幂等键。客户端在响应丢失后重试可能重复创建。需定义请求 ID、重试语义和事务边界，并测试“已提交但客户端未收到响应”。

### P1：重建业务边界

4. **通知读取承担修复写入。**
   已移除通知列表和未读计数中的 `backfillCommentNotifications`。新评论在写入后生成幂等通知，读取接口只读取通知投影。历史通知回填仍是上线前迁移任务，必须由受控、可观测的后台任务执行，不能再由用户读取触发。
5. **评论轮询重复获取全量数据。**
   `watchComments` 每 6 秒调用 `getCommentsByPost`，后者循环分页取完评论再构树。评论量增长会增加每次刷新成本。需要分页展示、增量更新协议及前后台生命周期管理。
6. **页面承担业务编排。**
   编辑器页面同时管理自动保存、并发保存、离线恢复、发布、草稿删除和导航。应提取独立编辑会话模块，页面只负责输入与展示；对保存中继续输入、发布失败、退出页面等行为做回归验证。
7. **服务端入口混合多类职责。**
   消息入口约 560 行，用户入口约 457 行；问题是权限、业务规则、数据库访问、外部服务和响应映射集中，而不是单纯文件长。优先围绕业务用例拆分，不为每个函数机械增加抽象层。
8. **接口类型没有运行时约束。**
   `callCloud<T>` 最后通过类型断言返回数据，服务端仍为 JavaScript。应定义请求与响应契约、统一错误码，服务端验证输入，客户端在边界验证关键响应。公共响应改为明确字段映射，减少数据库字段扩展意外影响客户端的风险。
9. **限流故障策略隐含在公共工具中。**
   `checkRateLimit` 在存储失败时返回 `allowed: true, degraded: true`，现有测试也固定了该行为。需要按操作明确故障策略和告警，不能把全局修改当作无行为变化的整理。

### P1：发布工程

10. **发布过程需要可复现与可回退。**
    当前发布脚本硬编码环境，部署前复制公共工具，并逐个上传云函数。需改为显式环境选择、构建目录产物、依赖锁定、版本记录和兼容发布顺序。公共工具复制有单函数上传边界的原因，应让构建系统管理它。
11. **关键上线条件尚未验证。**
    数据库权限与索引目前主要由文档指导配置；应在隔离环境验证。认证当前暂停而写操作要求已认证用户，正式开放前需明确新用户进入完整业务流程的方案。

## 目标结构

前端：页面/组件 → 业务功能模块（编辑、会话、消息同步等）→ API 与本地存储适配。

服务端：云函数入口（身份上下文、校验、错误转换）→ 业务用例（权限规则、状态转换、事务编排）→ 数据库及邮件等适配。公开响应通过独立映射生成。

按身份、内容、互动、消息划分模块。模块拥有自己的规则和存储访问；跨模块操作通过明确接口协作。保留现有云函数名称和接口兼容层，让客户端与服务端能够分批发布。

## 实施顺序与验收

| 阶段 | 交付 | 验收要求 |
|---|---|---|
| 0 功能基线 | 功能/权限矩阵、现有接口契约、关键行为测试 | 游客/未认证/已认证/管理员、匿名作者/非作者行为明确；关键测试验证返回值与数据库副作用 |
| 1 消息正确性 | 同步游标、完整会话模型、数据回填 | 同时间超页消息无遗漏；超过当前扫描上限仍能查到旧会话；未读数与基准查询一致；重复回填不重复计数 |
| 2 内容写入 | 发帖/评论幂等、事务与通知补偿 | 重试不重复创建；计数与内容状态一致；通知失败可恢复；匿名响应不暴露作者身份 |
| 3 客户端状态 | 编辑会话模块、分页评论、统一请求生命周期 | 自动保存不覆盖新输入；登出后旧响应不恢复私有状态；离开页面停止刷新；各用户本地数据隔离 |
| 4 发布闭环 | 构建产物、环境配置、日志与发布/回滚流程 | 隔离环境验证权限和索引；真实设备关键流程通过；完成升级与回滚演练 |

每阶段都包含契约、实现、测试和迁移，不先大规模移动文件再补测试。业务变化与结构调整分开记录，保留可回退路径。性能预算应基于预期用户量及隔离环境测量制定，本次不虚构容量或重构工期。

第一批推荐交付为阶段 0 与消息游标修复：范围可控，并能验证新的模块边界和测试方式。全项目重构完成与具备上线条件是两个不同的验收结论，均不能由当前 30 项测试单独证明。
