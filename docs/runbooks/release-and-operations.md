# 发布、迁移与运行治理

状态：运行手册框架，R7 必须替换为与实际工具对应的可执行步骤；本文不意味着当前已完成部署或演练。

## 环境和配置

开发、隔离测试、正式环境明确区分。环境 manifest 描述小程序 AppID、CloudBase 环境、运行时、云函数配置、集合/索引/权限版本、功能开关、依赖与产物版本。

客户端可见配置和服务端秘密分开构建。邮件凭据、部署密钥、匿名身份映射等不进入 Git、日志、测试快照或客户端包。环境 ID 本身不是秘密，但不能让发布脚本隐式选中正式环境。

运行时支持矩阵必须通过平台实际配置及官方资料核实；当前 cloudbaserc 的 Nodejs16.13 和本地文档的 Node 20+ 是不同事实，不能仅改 target 掩盖不兼容。

## CloudBase CLI 上线前核验

本节只用于确认本机身份和目标环境，不发布函数、不创建集合或索引、不修改权限。执行人先在自己的终端确认 CLI 可用：`tcb --version`；再执行只读查询：`tcb env list --json`。后者必须返回有效身份下可见的环境列表。若提示没有有效身份，先完成 CloudBase 登录，再重新执行；不得以猜测的环境 ID 继续发布。

从列表中选定的环境必须与 `cloudbaserc.json` 的 `envId`、本次发布记录和小程序配置逐项一致。随后在该环境的控制台或已经核实语法的 CLI 命令中，记录函数运行时、已部署版本、集合权限和索引实际状态，并与 [开发说明](../DEVELOPMENT.md) 的索引清单对照。当前仓库尚未完成这一实测，因此这一记录是 R8 的前置证据，不是通过声明。

核验完成后才可准备隔离环境冒烟和发布产物。正式发布仍遵循下文顺序，并且由使用 `dist/cloudfunctions` 的部署流程执行；本节的任一命令都不应触发部署。

## 管理网页的 CI/CD

管理员云端结构准备使用 `npm run provision:admin-cloud` 先查看差异，再使用 `npm run provision:admin-cloud -- --apply` 应用。工具按唯一schema保留现有数据和索引、补缺失集合/索引，并逐集合读回ADMINONLY；遇到不兼容的唯一索引报告冲突，不自动删除。备份与检查点在 `dist/admin-cloud-schema/<环境ID>/`，必须确认applied.json的completed为true且conflicts为空。已有分类先运行 `npm run migrate:admin-categories`，核实备份和保护对象后加 `-- --apply` 补齐管理版本。云函数部署使用构建后的dist/cloudfunctions，与静态网页分别发布；不能仅上传网页就认为新接口已生效。

管理网页是静态托管的 `/admin` 子路径。`Verify` 工作流在每次推送和合并请求运行完整 `npm run check`，其中包含网页严格类型检查和生产构建。`Deploy admin` 仅在 `main` 推送或人工触发后运行；其再次完成完整检查，才运行 `npm run deploy:admin`。

部署工作流使用 GitHub 的 `production` Environment，必须在该 Environment 中配置 `CLOUDBASE_SECRET_ID` 和 `CLOUDBASE_SECRET_KEY` 两个密钥。它们是可部署到已配置 CloudBase 环境的腾讯云 API 凭据，不能写入 `config/project.json`、仓库、网页包或 Actions 日志。工作流从公开的 `config/project.json` 读取唯一目标环境，使用项目锁定的 CloudBase CLI，以安全备份和本地远端文件清单核对上传 `/admin`；不会删除托管根目录或其他路径。

首次启用前，在 GitHub 保护 `production` Environment，限制可部署分支为 `main`，并由实际环境管理员保存上述密钥。之后任何 `main` 提交只有在验证和 Environment 审批通过后才会发布。密钥缺失或无目标环境权限应使部署明确失败，不能回退到别的环境或模拟成功。

## 构建产物与发布单元

每次发布记录版本、源代码状态、依赖锁摘要、构建命令、环境、各函数产物摘要、schema/迁移版本和受支持客户端协议。脏工作区构建可用于本地验证，正式发布应能定位完整源码快照。

小程序与每个云函数分别生成产物；CI 检查和实际部署使用同一产物。禁止线上临时安装未锁定 latest 依赖或部署脚本运行中修改业务源码。

函数部署部分失败必须返回失败并列出成功/失败版本，不输出“全部成功”。发布顺序考虑跨函数兼容，不能假设多个函数同时切换。

## 发布顺序

1. 核对环境、可恢复备份、权限/索引、旧客户端支持范围和回退产物。
2. 先部署兼容新旧记录/协议的服务端版本，执行只读冒烟。
3. 分批执行可重入迁移，记录检查点；验证全量计数、抽样身份/匿名映射与并发新写覆盖。
4. 在隔离环境启用新读路径和后台补偿，完成真实事务、失败恢复、设备验证。
5. 发布客户端并观察错误、延迟、重试、事件积压与旧协议使用；功能开关变更写审计。
6. 满足兼容退出条件后移除旧入口/字段/读时修复；删除数据属于单独迁移，不与首次切换绑定。

上述是顺序约束，具体命令须由 R7 从真实实现填入，并能在普通终端重现。执行正式发布的时点由后续任务的实际范围确定，本轮规划交付不代表已执行任何外部变更。

## 回退与恢复

- 代码回退只适用于旧实现仍能读取当前数据的兼容窗口；破坏性数据变更不能承诺“一键回滚”。优先添加式 schema，必要时采用前向修复。
- 每项迁移说明备份范围、还原步骤、可丢失范围、停写需求、核对步骤和失败重试；恢复时不得覆盖迁移开始后的合法新数据。
- 受控停写/关闭功能用于防止继续扩大已确认的数据损坏；公开浏览尽可能保持。开关失败行为和缓存刷新方式要有测试。
- 备份不等于完成恢复能力：在隔离环境至少一次恢复并核对。没有真实演练证据时 R8 保持未完成。

## 可观测性

结构化日志至少含 requestId、action、版本、耗时、结果码和环境；跨 outbox/消费者携带关联标识。禁止把请求 event、完整数据库记录和错误响应体不加筛选地输出。

应能观察：身份/权限失败率、API 错误和延迟、消息同步滞后/重同步、幂等命中和冲突、事务重试、计数不一致、通知积压/最终失败、轮询次数、数据库调用与费用趋势。

告警分为需立即处理的隐私/数据完整性异常、服务不可用、后台积压/成本偏离。阈值基于明确的环境与基线配置，记录处理入口；不为无人接收的告警堆砌指标。

管理操作审计记录操作者、目标、动作、结果和关联版本，避免记录不必要正文及身份信息。普通业务日志与审计用途/保留权限区分。

## 故障处理清单

| 故障 | 应具备的处理路径 |
|---|---|
| 私信或匿名身份泄露 | 定位受影响接口/版本，收紧入口，保留最小审计证据，修复与回归；不在普通工单复制泄露数据 |
| 同步遗漏/未读漂移 | 确认游标与会话作用域，受控重新同步，运行核对/重建投影；不直接清空历史消息 |
| outbox 积压 | 查看认领与失败原因，修复消费者，重放去重事件，核对完成水位 |
| 邮件服务失败 | 保持认证暂停，保留原有认证状态；恢复需服务端真实验证后再开放入口 |
| 限流/数据库故障 | 按动作的降级策略处理，保留离线草稿，排查依赖；不全局放开权限或限流 |
| 部分部署失败 | 查看产物版本矩阵，完成兼容回退或前向恢复，再运行冒烟 |

## 上线剩余政策

用户已要求完整设计上线保护，具体实施使用 [goal 入口](../plans/community-safety-goal.md)。默认无人工预审、正常内容自动检查通过即发布；仅微信／CloudBase及现有邮件服务依赖，不增加审核商或AI。旧协议直接切换，无双写／fallback；迁移保留已有账号认证。用户已备案，编号只做真实展示核对。

校园社区的主体/类目/匿名准入、协议隐私、内容治理、用户权利、属地办理和最小首发顺序见[上线准备手册](launch-preparation.md)，代码及官方规则证据见[上线准备审查](../audits/launch-readiness-2026-09-21.md)。按实际首发能力关闭门槛；完成状态统一记录在status，不以本手册框架存在当作演练完成。

邮箱认证恢复、真实内容审核能力、用户隐私/保留政策、服务支持范围与运营责任需在开放前有明确结论；代码重构不自动证明这些条件已满足。无需为缺少这些结论暂停本地迁移，但不得把它们标记为已验收。
